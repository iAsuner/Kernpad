# Security policy

[简体中文](SECURITY.zh.md)

Kernpad 1.0.0 is the current supported source line. It has not undergone an independent third-party security audit. Passing tests, ad-hoc signatures and self-signed packages are not security certifications.

## Reporting a vulnerability

Use [GitHub private vulnerability reporting](https://github.com/iAsuner/Kernpad/security/advisories/new) when enabled for the repository. If that option is unavailable, open an issue asking the maintainer for a private reporting channel **without including exploit details or sensitive material**. Do not upload real passwords, recovery keys, private keys, personal libraries or unredacted screenshots.

Include the application version, operating system, relevant configuration, reproduction steps, expected and actual behavior, and a minimal synthetic example. Explain the affected trust boundary and potential impact. No response-time or bounty commitment is offered.

## What is protected

| Data | Protection |
| --- | --- |
| Vault records, confidential documents and their media | Individually encrypted records under an encrypted vault index |
| Public notes and explicitly public OTP seeds | Plain text in the local library |
| Template definitions and ordinary template samples | Public structural data; actual credential values are cleared when saving a template by default |
| Uncommitted vault drafts | Separate encrypted local drafts; excluded from backups |
| Encrypted backups | New envelope and per-record re-encryption; recovery uses system authentication with the original vault, or its recovery key |
| Exported PDF, copied values and screenshots | Outside vault protection; treat as disclosed content |

Vault encryption uses AES-256-GCM and a randomly generated 256-bit root key. Recovery uses a random 256-bit key and HKDF-SHA256, not a user-chosen password. Interactive cooldowns slow repeated failures in the current process; offline attack resistance comes from the entropy and secrecy of the recovery key.

macOS uses a Secure Enclave key with `userPresence`, enforced at the private-key operation. Windows uses Windows Hello private-key operations with TPM attestation checks. The Windows success path still requires dedicated validation on supported physical hardware. Unavailable or cancelled authentication must leave the vault locked.

## Limits and review priorities

The app does not protect against a compromised OS or application process, malicious repackaging, every plaintext memory copy, or replacement with an older fully authenticated library. Clipboard clearing cannot recall copies already made elsewhere. Temporary-note expiration is not secure media erasure and cannot remove external backups or snapshots.

Security-sensitive changes must preserve native bridge allowlists, local-origin restrictions, HTML sanitization, safe media handling, session tickets, explicit deletion IDs, atomic writes and failed-save retention. Format and signing identity changes require a migration design. See the [architecture](docs/architecture.en.md) and [user guide](docs/guide.en.md#backup-recovery-and-security).

## Public test material

Tests and example accounts use synthetic data. `Source/Tests/Fixtures/interop-v3-backup.json` intentionally includes a synthetic recovery value so Swift and .NET can verify the same fixture; it is generated by `InteropFixture.swift` and never protects a personal library. The sample OTP seed is the Base32 representation of the public SHA-1 test secret from [RFC 6238, Appendix B](https://www.rfc-editor.org/rfc/rfc6238#appendix-B).

Secret scanning keeps default Gitleaks rules enabled. Its exception is limited to that exact RFC seed in named example/test files. A clean scan is one review step; inspect screenshots, dependency changes and release archives separately.
